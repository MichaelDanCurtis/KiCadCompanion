# BL-09 — Generate and verify firmware offline

Status: proposed; not activated. Phase: Disciplines.
Prerequisites: BL-04, BL-06, BL-07. Read [the shared execution contract](../GOALS.md) before starting.

## Outcome

Build firmware for the selected ESP32 target from the approved hardware contract and demonstrate meaningful automated behavior tests before flashing.

## Scope and reuse

Firmware source and pinned ESP-IDF toolchain in a disposable/reference project; serial interaction and flashing are explicitly outside this offline goal.

Reuse first: CodexAgent execution/events, action gate, project pin/interface records, workflow evidence and UI logs.

## Deliverables

- Versioned pin/interface contract with generator or validator linking firmware configuration to hardware revision.
- Reproducible build command, lock/config records, firmware binary manifest, and host/simulator tests for protocol behavior.
- UI build/log/artifact view that reports generated versus built versus device-tested distinctly.

## Acceptance criteria

- [ ] **BL-09-A1** — A clean build with documented pinned target/toolchain succeeds and records source, board contract, configuration, and binary hashes.
- [ ] **BL-09-A2** — A deliberate pin-contract mismatch, reserved-pin conflict, wrong target, or out-of-date hardware revision fails validation.
- [ ] **BL-09-A3** — Behavior tests cover valid/invalid requests, timeout/error handling, and safe startup defaults using approved requirements, not just compilation.
- [ ] **BL-09-A4** — Generated code and build artifacts contain no credentials or machine-specific required paths; another fresh workspace can reproduce the build workflow.
- [ ] **BL-09-A5** — No device is flashed and no hardware-tested claim is made; the bring-up plan names exact future device identity and measurements.

## Verification

Clean reference firmware build, automated host/simulator tests, deliberate contract mismatch, and generated artifact inspection. If behavior cannot be simulated, state the specific untested hardware-dependent functions.

Record each criterion in [the evidence record](../evidence/BL-09.md) using the shared template. That record is created when work starts; absence means no evidence yet. Record commands, exit codes, tool versions, input/output revisions, before/after observations, and any manual test steps. A baseline failure remains a finding, not an excuse to delete or skip a required test.

## Blockers and authority

Unknown electrical facts, missing module-specific SDK support, unavailable toolchain, or undefined behavior requirements.

## Non-goals

No flashing, eFuse/boot-security changes, secret provisioning, OTA deployment, or claims about actual timing/electrical behavior from simulation.
